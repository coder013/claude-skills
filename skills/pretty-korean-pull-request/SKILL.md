현재 브랜치의 변경 사항을 바탕으로 한국어 PR을 작성하고 생성한다.

핵심 원칙: **길이는 담을 항목을 골라서 줄이고, 문장은 압축하지 않는다.** "짧게"는 2단계(추리기)에서, "자연스럽게"는 3단계(쓰기)에서 처리한다.

## 1. 수집

1. base 브랜치를 정한다. 사용자가 지정하지 않았으면 저장소 기본 브랜치를 쓴다.
   ```bash
   gh repo view --json defaultBranchRef --jq .defaultBranchRef.name
   ```
2. 변경 범위를 수집한다.
   ```bash
   git fetch origin <base>
   git log --no-merges --format='%h %s%n%b' origin/<base>...HEAD
   git diff --stat origin/<base>...HEAD
   git diff origin/<base>...HEAD
   ```
3. 커밋이 하나도 없으면 PR을 작성하지 않고, 변경 사항이 없다고 알린 뒤 종료한다.
4. PR 템플릿이 있는지 확인한다: `.github/pull_request_template.md`, `.github/PULL_REQUEST_TEMPLATE.md`, `docs/pull_request_template.md`, `pull_request_template.md`. 있으면 3단계에서 기본 템플릿 대신 그 섹션 구조를 따른다.

## 2. 추리기

### 티켓 번호

`[A-Z]+-[0-9]+` 패턴을 아래 순서로 찾는다.

1. 브랜치 이름 (`git branch --show-current`). 있으면 커밋 메시지는 보지 않는다.
2. 1단계에서 수집한 커밋 메시지.
   - 한 종류만 나오면 그 번호를 쓴다.
   - 서로 다른 번호가 두 개 이상 나오면 임의로 고르지 말고, 후보를 보여 주고 사용자에게 묻는다.
3. 둘 다 없으면 티켓 없이 진행한다.

### 섹션별 내용

각 섹션은 한 가지 질문에만 답한다. 같은 내용을 두 섹션에 쓰지 않는다.

| 섹션 | 답하는 질문 | 분량 |
|---|---|---|
| Summary | 왜 바꿨고, 결과가 무엇인가 | 1문장 |
| Changes | 무엇이 달라졌는가 | 1~3개, 임팩트 큰 순 |
| Impact | 리뷰어가 놓치면 안 되는 영향은 무엇인가 | 해당 항목만 |
| Testing | 어떻게 확인했는가 | 명령어나 시나리오 1~2개 |

- **Changes는 파일이 아니라 동작을 기준으로 쓴다.** `auth.ts 수정`(X) → `만료된 토큰으로 요청하면 401을 반환합니다.`(O)
- 변경이 많으면 임팩트가 큰 1~3개만 남기고 나머지는 버린다. 리팩터링, 이름 변경, 포맷팅처럼 동작이 바뀌지 않는 변경은 핵심이 아니라면 쓰지 않는다.
- Impact에는 호환성 깨짐, 마이그레이션, 설정이나 환경 변수 변경, 성능 변화, 다른 팀이나 시스템에 미치는 영향만 쓴다.
- Testing에는 실제로 확인할 수 있는 근거만 쓴다. 커밋과 diff에서 테스트 근거를 찾지 못했으면 지어내지 말고 `- 없음`으로 둔 뒤, 4단계에서 사용자에게 묻는다.
- 커밋과 diff에서 변경 이유를 찾지 못했으면 Summary에는 결과만 쓰고, 4단계에서 사용자에게 이유를 묻는다.
- 내용이 없는 섹션은 지우지 않고 `- 없음`으로 남긴다.

## 3. 쓰기

먼저 [references/fluent-korean.md](references/fluent-korean.md)를 읽고, 그 지침을 PR 제목과 본문의 한국어 문장에 적용한다. 지침은 요약하지 말고 예시까지 그대로 참고한다.

### 제목

```
type(TICKET-123): 설명
type: 설명            ← 티켓 번호가 없을 때
```

- `type`: `feat`, `fix`, `refactor`, `perf`, `test`, `docs`, `chore` 중 하나. 수집 범위에서 **가장 처음 커밋**을 기준으로 정한다. 그 커밋 메시지에 conventional prefix가 있으면 그대로 쓰고, 없으면 그 커밋의 변경 내용으로 판단한다.
- 설명은 한국어로 쓰고 명사형으로 끝맺는다. 단, 단어 사이의 관계가 드러나도록 조사는 생략하지 않는다.

```
O  fix(CSP-1879): 배포 후 Jira 완료 처리를 커밋 범위 수집에서 배포 대기 티켓 역대조로 전환
O  fix: 만료된 토큰으로 요청하면 401을 반환하도록 수정
X  fix: 만료 토큰 401 반환 처리
```

### 본문

PR 템플릿이 없으면 아래 형식을 그대로 쓴다.

```markdown
## 💡 Summary

- 

## 🛠️ Changes

- 

## ⚠️ Impact

- 

## 🔍 Testing

- 
```

- 모든 불릿은 합니다체 종결어미로 끝맺는다.
- 길이를 줄이려고 조사와 어미를 빼지 않는다. 짧게 만들려면 항목 수를 줄인다.
- 코드 식별자, 명령어, 파일 경로는 원문 그대로 백틱으로 감싼다.
- 배경 설명, 인사말, 마무리 문장을 쓰지 않는다.

```
X  - 토큰 만료 검증 추가. 리프레시 시 기존 토큰 무효화.
X  - 토큰 만료 시각을 검증하고, 만료되었다면 401을 반환함
O  - 토큰 만료 시각을 검증하고, 만료되었다면 401을 반환합니다.
O  - 리프레시 토큰을 재발급할 때 기존 토큰을 즉시 무효화합니다.
```

## 4. 점검과 확인

1. 출력하기 직전에, 작성한 제목과 본문에서 fluent-korean 지침과 위 규칙에 어긋난 부분을 점검하고 수정한다. 특히 아래 항목을 확인한다.
   - 조사나 어미가 빠진 명사구 나열이 없는가
   - 합니다체가 아닌 불릿이 없는가
   - 두 섹션에 같은 내용이 반복되지 않는가
   - Changes가 3개를 넘지 않는가
2. 제목과 본문 초안을 사용자에게 보여 주고 승인을 받는다. **승인 전에는 PR을 생성하지 않는다.** 2단계에서 테스트 근거나 변경 이유를 찾지 못했다면, 초안 아래에 해당 질문을 함께 붙여서 한 번에 묻는다.
   ```
   확인이 필요합니다.
   - 이 변경을 어떻게 테스트하셨나요? (없으면 그대로 둡니다)
   - 변경한 이유가 무엇인가요?
   ```
   사용자가 답하면 해당 섹션을 고쳐서 다시 보여 준다.
3. 사용자가 수정을 요청하면 초안을 고쳐서 다시 보여 주고, 다시 승인을 받는다.
4. 승인을 받으면 원격 브랜치 상태를 확인한다.
   ```bash
   git rev-parse --abbrev-ref --symbolic-full-name @{u}   # 실패하면 upstream 없음
   git status -sb                                          # [ahead N]이면 푸시 안 된 커밋 있음
   ```
   upstream이 없거나 푸시하지 않은 커밋이 있으면, 푸시할지 사용자에게 묻는다. **승인 없이 푸시하지 않는다.** 승인을 받으면 `git push -u origin HEAD`를 실행한다.
5. 본문을 임시 파일에 저장하고 PR을 생성한다. 이모지와 백틱 때문에 셸 인용 문제가 생기지 않도록 `--body-file`을 쓴다.
   ```bash
   gh pr create --base <base> --title "<제목>" --body-file <본문 파일>
   ```
6. 생성된 PR의 URL을 알린다.
